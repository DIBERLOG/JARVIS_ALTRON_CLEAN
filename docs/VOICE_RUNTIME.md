# Быстрая озвучка JARVIS

Выбранный локальный голос: XTTS после доработки, сессия `20261004-131203`.
Профиль: `jarvis_ru_012.wav`, скорость 1.0, seed 28, temperature 0.42,
top_p 0.72. Дополнительные эквалайзеры и изменение высоты голоса отключены.
Предыдущие модели и записи не удаляются.

## Как устроен ответ

- Записанные ответы команд остаются MP3: их не нужно синтезировать.
- XTTS загружается в фоновом процессе один раз и сохраняет conditioning.
- Подготовка модели не блокирует очередь готовых MP3.
- Повторяющиеся реплики берутся из локального WAV-кэша
  `%LOCALAPPDATA%/JarvisVoiceStudio/speech-cache`.
- Ответы Ollama и DeepSeek принимаются потоково и озвучиваются по закончённым
  предложениям, не дожидаясь всего ответа. Русский текст передаётся в UTF-8
  между Rust и Python на Windows; регрессионная проверка контролирует WAV-кэш
  именно для исходной русской строки, а не искажённых букв.
- В `%LOCALAPPDATA%/JarvisVoiceStudio/speech-latency.jsonl` фиксируются время
  подготовки звука и запуска воспроизведения, без сохранения текста вопроса.
- Отмена озвучки сбрасывает текущую очередь; отменённый поток не добавляет новые фразы.
  После принудительной остановки голосовой процесс загружается снова при следующем ответе.
- Внутри вопроса допускается пауза около 2.2 секунды; завершённые части
  распознавания объединяются до отправки вопроса.

## Ограничения

Первый прогрев требует времени. Измеренный локальный no-play smoke-test:
прогрев 17.813 с, первая короткая фраза 4.937 с, повтор из кэша менее 0.001 с.
Это не полная задержка разговора: сеть, языковая модель и воспроизведение сюда не входят.
На GPU с 8 ГБ одновременные XTTS и крупная локальная языковая модель могут
не поместиться. Провайдер DeepSeek не меняется автоматически на Ollama.
Для Ollama запросы отключают thinking, используют контекст 2048 и keep_alive 15m.
Для DeepSeek разговор и чат отправляют thinking.type=disabled: иначе модель
может израсходовать весь max_tokens на reasoning_content без финального ответа.
Уже установленная qwen3:4b-instruct — меньший локальный вариант; выбор модели
остаётся в настройках пользователя.

## Проверки

В голосовом разговоре озвучивается полный ответ после окончания запроса:
потоковое разбиение отключено по просьбе пользователя. В текстовом чате
короткие предложения объединяются попарно перед синтезом; длинное завершённое
предложение (от 120 символов) можно отправить отдельно. Произвольного разрезания
по пробелу нет. Это сокращает число стыков, но может немного задержать начало
первой короткой реплики. При воспроизведении добавляется 80 мс тишины для
завершения вывода на устройство; сохранённый WAV и параметры голоса не меняются.

Голосовые ответы по умолчанию ограничены 2–3 предложениями инструкцией модели
(попросите «подробно» для развёрнутого ответа). Новостные RSS загружаются параллельно.
Веб-поиск включается для свежих тем и явных просьб «найди в интернете», «проверь
в сети»: Google News RSS для новостей, DuckDuckGo HTML для общего поиска.
Bing RSS отключён: на проверенных русскоязычных запросах возвращал постороннюю выдачу.
Общий поиск подключается напрямую (no_proxy); Google News и API DeepSeek сохраняют
прежнее подключение. Явный запрос поиска работает и вне разговорного режима.
Один обработчик используется голосовым модулем и WEB INTEL в чате. Поисковый запрос
очищается от вводных слов и вежливых обращений. Ошибка поиска передаётся
модели как ограничение, а не прерывает разговор. Даты без подтверждения не добавляются.

Разговор включается командой «давай поговорим», а не при запуске модуля,
и остаётся активным до «закончи разговор», «режим команд»
или «отмена» (если не отменяется текущий уточняющий диалог центра). Тишина не
выключает режим. «Давай поговорим» повторно включает его; в том числе после
распознавания через классификатор команд, а не только точного совпадения фразы.
IPC dialogue_mode передаёт реальное состояние при смене режима и подключении GUI.
Центральный реактор остаётся активным в разговоре, кроме отключения микрофона
или потери связи. Новости конкретной темы сначала ищутся через Google News RSS.

`tools/voice_training/test_resident_xtts.py` проверяет постоянный процесс без
проигрывания аудио и повторный запрос из кэша. Rust-тесты проверяют границы
предложений и оба формата потокового ответа на локальном тестовом сервере.
Основная модель находится вне поставляемого EXE: приложение использует
`resources/tts/trained-checkpoint.txt` и локальные файлы указанной сессии.
